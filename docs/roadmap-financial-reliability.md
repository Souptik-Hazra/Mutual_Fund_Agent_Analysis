# Authoritative Delivery Roadmap — Mutual Fund Agent Analysis

**Repository:** `Souptik-Hazra/Mutual_Fund_Agent_Analysis`  
**Default branch:** `main`  
**Operating model:** Personal, local-first Indian mutual-fund research application  
**Supported CI:** Python 3.11 backend; Node.js 22 frontend

## Current project baseline

Phases 0–21 and P0/P1 have previously been delivered on `main`. The existing FastAPI, PostgreSQL, React/Vite, LangChain/LangGraph, deterministic financial analytics, fund/category/portfolio intelligence, security observations, events, social research and document retrieval capabilities must be extended rather than rebuilt.

Financial calculations remain deterministic backend operations. LLMs may route, retrieve and explain evidence, but must not calculate or overwrite NAV, returns, XIRR, portfolio exposure or other financial values. Qdrant remains optional and private; PostgreSQL lexical retrieval is the fallback.

### P2 external acceptance gates and reproducible validation

These gates are not satisfied by mocks or by the green offline evaluation. Keep each item open until the stated external evidence exists.

- **P2-01 — AMC disclosure samples:** Obtain the original official PDF/XLSX/CSV disclosure, publication URL/date and header/field notes for each supported AMC. Register a distinct source key with mfa-register-source, keep it disabled until its authority/terms are checked, then map the real fields into the existing normalized portfolio CSV/XLSX importer. Retain one sanitized representative input and expected normalized rows per AMC. Do not claim an AMC-specific adapter from a generic header-normalization test.
- **P2-02 — scheme lifecycle and expense-ratio history:** Obtain an authoritative dated scheme-master/expense-ratio source file with effective dates and lifecycle/rename/merger evidence. Register the source, import through mfa-import-scheme-metadata <file.csv> --source-key <key> (default unverified), compare rows to the original, then re-import as verified only after manual review. Reconcile at least launch, rename/merger and closure transitions against source history.
- **P2-03 — IDCW notices:** Obtain original official distribution notices with scheme/option, ex-date, record date, payment date, per-unit amount and notice/revision identifiers. Import using mfa-import-idcw <file.csv> --source-key <key>; for corrections increase revision and set supersedes_distribution_id. Reconcile the full requested date interval to the source distribution list before creating a separate verified coverage attestation. CSV import deliberately never creates that attestation.
- **P2-04 — AMFI/MFAPI/Nifty live validation:** With a known scheme code and a Nifty TRI benchmark code, run a bounded read-only 31-calendar-day probe: mfa-audit-local --live --scheme-code <scheme-code> --benchmark-code <nifty-tri-code> --start-date YYYY-MM-DD --end-date YYYY-MM-DD --output artifacts/live-provider-audit.json. Keep the generated report, including provider errors, matched NAV dates, conflicts, duplicate/out-of-order and window-quality checks. Repeat a separately scoped interval if broader coverage is needed.
- **P2-05 — Twelve Data entitlement:** Supply a valid local TWELVE_DATA_API_KEY and explicit confirmation that the account is permitted to query the selected NSE/BSE exchange via TWELVE_DATA_EXCHANGE_ACCESS_CONFIRMED=true. Add --twelve-data-symbol <symbol> --twelve-data-exchange <exchange> to the same bounded mfa-audit-local --live command. Save the returned symbol, exchange, timestamp and outcome. A successful response validates only that one quote request, not historical prices, full fundamentals or plan-wide entitlement.
- **P2-09 — Reddit/X terms and access:** A human must review current platform terms, account plan, endpoint scope, attribution and retention rights. Record terms_url, terms_reviewed, access_confirmed and reviewed_at in the registered social source metadata using mfa-register-source --metadata-json; keep the source disabled until review is complete. Re-review if terms or account entitlement changes.
- **P2-10 — quantitative parity expansion:** Add deterministic service-derived fixtures and per-specialist labelled cases for multi-fund comparisons, category rankings, investor ledger valuation/XIRR, portfolio overlap/allocation, security observations and historical event selection. Include missing/empty/insufficient-history, stale, malformed, future-dated, mixed-category and unequal-window cases. Report numeric exact/tolerance parity separately from routing accuracy and evidence-contract accuracy; do not infer numerical parity from the 20-case intent-routing score.

## Actual exposure and benchmark fallback implementation (2026-11-26)

The actual-exposure analytics accepts a calendar `as_of_date`, filters investor transactions to that date, chooses the newest reconciled NAV row on or before the date before inspecting its status (a latest conflict blocks valuation), and selects the latest complete/partial holdings snapshot effective on or before the date. Responses expose per-fund NAV date/status/age, selected valuation date, excluded funds, missing/partial disclosure and data-quality warnings, and look-through coverage. The request schema, assistant specialist propagation, GET query parameter and React panel carry the valuation date. Expected-value regression fixtures cover 10 units × ₹20 NAV = ₹200, 40% holding = ₹80, future transactions, latest NAV conflict refusal, and partial disclosures.

Benchmark lookup errors now propagate rather than being silently converted to unmapped status. Retrying without benchmark data is restricted to the API's explicit HTTP 422 no-TRI-observations response. Frontend tests cover genuine missing observations and unrelated 404/422/500 errors.

The following wider numeric-parity work remains open: independent expected-value fixtures for multi-fund comparisons, category rank outputs, full portfolio allocation and overlap calculations, unequal history windows, and systematic missing/stale/partial data cases. The focused tests above must not be interpreted as completing P2-10.

## CI and Git workflow contract

- All implementation changes are committed directly to the existing `main` branch; no feature branches or pull requests.
- Backend CI is Python 3.11 only. Keep Node.js 22 frontend tests/build.
- Live-provider checks remain explicitly gated and must never be represented by mocked tests.
- Qdrant integration tests use disposable service/collections. Backup/restore uses an isolated Compose project and disposable volumes.
- Do not weaken test coverage or mark a priority complete solely because code or documentation was added.

## Completion criteria

P2/P3 are complete only when every remaining external gate above has been either verified with evidence or explicitly documented as unavailable, the complete backend/frontend/agent/backup CI is green on `main`, the frontend lockfile is committed and cache-keyed, and the final code review confirms that financial methodology, provenance, historical `as_of` behaviour and local-only security boundaries remain intact.

## Explicitly out of scope

Public hosting, multi-user accounts, cloud deployment, production authentication, multi-tenancy, automated investing/trading and public exposure of the local development API.
